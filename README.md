# 飞书 Perfecto → QQ 群转发器

这是一个只在本机运行的转发工具。macOS 飞书通知仅用于唤醒；真实消息由飞书用户 API 从固定的 Perfecto 单聊和四个配置好的飞书群聊中读取，再通过 QQ 官方机器人 API 转发到已绑定群。

当前支持普通文本和图片。文本按飞书 `message_id` 转发；图片先以飞书用户身份下载，再上传 QQ 取得 `file_info`，最后以 `RICH_MEDIA` 发送。

## 工作方式

1. Swift 程序通过 macOS 辅助功能订阅通知中心的 AX 事件。
2. 发现飞书通知后，只写一条不含正文和正文派生值的唤醒记录。
3. Python 转发器使用固定 profile `tenant-105183` 定位唯一 Perfecto 联系人和单聊，同时读取四个已配置的飞书群聊。
4. 根据各自持久化的消息游标拉取游标之后的消息，并按 `message_id` 去重。
5. 文本直接发送到 QQ；图片临时下载、上传和发送后立即清理。
6. 每条消息成功发送或明确跳过后才推进游标；发送失败不会越过该消息。

通知与消息不是一一对应关系。macOS 可能把连续同文消息折叠成汇总通知，因此通知只负责触发一次 API 同步；一次触发可以取回多条消息。重复通知再次触发时，游标会使结果为空，不会重复转发。

## 前置条件

- macOS 已运行飞书客户端，并允许本程序使用“辅助功能”。
- `lark-cli` 中存在并已授权 profile `tenant-105183`，对应用户为“用户105183”。
- 该账号与 Perfecto 有唯一的点对点会话。
- QQ 机器人密钥已保存在 macOS 钥匙串，目标群已经绑定并允许机器人主动发言。
- Python 3.12、Swift 5.10 或更高版本。

所有飞书 CLI 请求都会显式携带 `--profile tenant-105183`，不会切换或依赖默认 profile。

## 首次检查与绑定

创建 Python 环境并安装 QQ 官方 SDK：

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-qq.txt
```

检查飞书用户授权、Perfecto 固定会话、QQ 凭证和网关：

```bash
.venv/bin/python qq_bridge.py check \
  --lark-profile tenant-105183 \
  --lark-contact Perfecto
```

如尚未绑定 QQ 群：

```bash
.venv/bin/python qq_bridge.py bind
```

如需在保留当前群的同时新增一个 QQ 群绑定，先停止转发服务，再执行：

```bash
.venv/bin/python qq_bridge.py bind --add
```

新增绑定完成后，Perfecto 和已配置频道会向所有 `active` 群发送；每个来源和目标群分别记录已投递消息，某个群发送失败不会阻塞其他群，也不会导致成功群在重试时重复发送。

随后在目标群发送 `@qclaw 绑定测试`。群主还需在手机 QQ 的“群设置 → 机器人 → qclaw → 机器人权限设置”中开启“机器人主动在群聊内发言”。

测试 QQ 主动文本消息：

```bash
.venv/bin/python qq_bridge.py test
```

## 启动转发

推荐双击唯一入口 `start.command`，启动网页控制面：

```bash
./start.command              # 启动网页控制面
```

- 构建 Release 版通知监听器；
- 从当前通知文件末尾建立或恢复字节游标；
  - 从 Perfecto 会话当前最新位置建立或恢复消息游标；
  - 加载四个频道的独立游标，收到对应飞书通知后自动同步；
- 同时启动通知监听器和 Python 转发器。

启动时不会重放通知文件中的历史唤醒记录。Perfecto、监听人员和四个频道都会从各自已确认的消息位置继续；监听人员与频道会在服务启动时统一立即补扫游标之后的积压消息，之后再由通知即时唤醒，并由低频巡检兜底。

按 `Control+C` 停止。脚本会同时结束通知监听器和转发器。

如果明确需要放弃尚未处理的历史记录并把两类游标都移到当前末尾，可手动执行：

```bash
.venv/bin/python qq_bridge.py prime \
  --force-end \
  --lark-profile tenant-105183 \
  --lark-contact Perfecto
```

## 第一阶段：本机 Web 控制面基础

`start.command` 会启动控制面并自动打开 `http://127.0.0.1:8765`。转发、绑定、补发和测试均从网页操作。

页面提供：

- 总状态和 Swift 通知监听、Python 转发任务的子进程状态；
- 启动、停止、重启操作。启动流程复用现有的 `probe`、`prime`、`run` 命令；
- 只读检查入口，检查失败不会发送 QQ 消息；
- 当前控制面会话中的脱敏事件，例如进程生命周期、只读检查和通知唤醒信号。

写操作同时需要本机同源请求和控制面启动时生成的短期令牌。控制面只会停止本次由它自己启动并持有的子进程，不按状态文件中的 PID 猜测或广泛结束进程；通过 `start-forwarder.command` 启动的独立会话仍按原来的 `Control+C` 方式使用。页面和 API 默认不展示 QQ 密钥、完整群/会话标识或本地图片路径；“查看待补发”弹窗仅按用户选择展示待处理消息摘要及图片资源键。

第一阶段的技术取舍是保留现有 CLI 和转发实现，把控制面作为独立的 Python 标准库进程管理层；前端采用无构建依赖的静态 HTML、CSS 和 JavaScript，并通过短轮询读取结构化状态。这样不会让 Web UI 解析终端输出，也不会与 QQ WebSocket 共用连接。

## 第二阶段：Web UI 操作

在第一阶段页面的基础上，第二阶段把现有 CLI 的绑定、主动测试和 prime 能力接入本机页面。页面仍然是无构建的静态 HTML、CSS 和 JavaScript，不使用外部资源，也不展示 QQ 密钥、完整群标识、会话标识或原始游标。

- 绑定会异步运行现有 `qq_bridge.py bind`。页面会显示未绑定、绑定中和已绑定；绑定中请在目标 QQ 群发送 `@qclaw 绑定测试`，可以取消当前绑定等待。重新绑定会调用现有 `bind --rebind`，页面确认和控制面 API 都要求二次确认。
- 页面提供“监听人员管理”，默认包含 Perfecto；新增人员会保存到本机 `.lark-listeners.json`，页面随后自动重启转发任务完成热更新，无需手动执行命令或重新打开页面。
- 主动消息测试调用现有 `qq_bridge.py test`，页面会明确提示它向真实 QQ 群发送测试消息，并展示进行中、成功或失败。失败时可按引导检查群主动发言权限后重试。
- 游标操作调用现有 `qq_bridge.py prime`。默认 prime 沿用原有语义：首次初始化从最新位置开始，已有游标继续使用，不补发历史消息。`从最新位置开始` 是明确的 `--force-end` 操作，会在二次确认后放弃当前未处理消息并从最新位置开始。
- 启动失败、发送失败、辅助功能权限失败和子进程退出都会给出检查、重试或重启引导。发送失败不会推进游标，页面不提供单条消息手动重发。

控制面只通过本次会话持有的本地子进程和状态文件判断操作结果，不解析终端输出。绑定、测试和 prime 的状态与事件均由 `/api/status` 以结构化 JSON 返回；所有写请求继续要求 `127.0.0.1` 同源和短期控制令牌。

## 第三阶段：指定频道补发

已为以下四个飞书群聊建立独立游标，基准为 2026 年 9 月 1 日 15:00（上海时间），只处理基准时间之后的消息：

- 骚神复盘~；
- 三川吴岳8-11；
- 新生代柚子(屏蔽问答)；
- 聪明小阿姨。

控制面新增“选择频道补发”。点击“查看待补发”会打开逐条清单，可勾选文字或图片消息后再补发；弹窗会随补发进度标记已处理条目。系统调用 `channel_replay.py`，把该频道游标之后的选中内容补发到当前已绑定的 QQ 群。每条消息发送成功或明确跳过后才推进对应频道游标；发送失败、取消补发或进程中断时，已完成部分会保留，剩余部分可再次补发。补发不会改变 Perfecto 单聊的现有转发游标。

转发服务启动后，四个频道也会自动同步新消息，使用与手动补发相同的频道游标。为避免自动转发和手动补发同时修改同一份游标，手动补发需要先停止转发服务；服务运行时页面会只读展示自动转发状态。

频道游标保存在本地 `.lark-channel-cursors.json`，不会提交到 Git，也不保存消息正文。页面只显示频道名称、游标是否就绪和操作状态，不显示频道标识、消息标识或原始游标位置。

## 2026-09-01 本机验收结果

- 普通文本通知可唤醒固定会话 API，并唯一定位真实消息 ID。
- 同一通知重复解析得到相同消息 ID。
- 两条连续同文消息在 API 中位置相邻、消息 ID 不同；游标模型会转发两条。
- macOS 会把第二条同文通知折叠成汇总通知，证明不能用通知正文或通知数量做去重。
- 飞书图片以用户身份下载成功，样本为 JPEG、196,240 字节、736 × 768。
- 同一图片通过 QQ 官方 SDK 上传取得 `file_info`，以 `RICH_MEDIA` 发送并在测试群可见。

## 隐私与限制

- 通知 JSONL 只保存唤醒所需的应用名、标题和时间，不保存消息正文或正文派生值。
- 飞书 API 返回的文本只在内存中处理；图片只存在于系统临时目录，发送结束后自动删除。
- `.qq-forwarder-state.json` 保存 QQ 群绑定列表（schema v3）、通知字节位置、飞书会话标识、消息位置和按群投递记录，不保存飞书正文或图片。
- 静音、关闭飞书通知、专注模式、飞书前台抑制通知或辅助功能权限失效时，macOS 可能不产生唤醒事件；没有唤醒事件就不会主动同步。
- 当前自动转发 Perfecto 单聊和四个已配置群聊中的普通文本和图片；Perfecto 只转发目标联系人发送的消息，群聊按频道转发可读取到的文本和图片。其他消息类型会记录类型并推进对应游标，不会误当文本发送。

## 转发效率基准与运行时指标

基准运行器位于 `benchmarks/benchmark_forwarder.py`，使用固定消息夹具和假的 QQ 发送端，不会连接真实账号。可分别运行 `--mode legacy` 与 `--mode optimized`，比较批量处理 p50/p95、吞吐、发送数和图片下载次数；具体用法见 `benchmarks/README.md`。

转发器运行时会在 `.qq-forwarder-metrics.json` 保存脱敏的来源级同步耗时、待处理数、成功/失败次数和最近同步记录。该文件只用于本机观测，不包含消息正文或原始账号标识。

转发进程同时将排查日志写入 `.qq-forwarder.log`（超过 5 MB 自动保留最近 3 个轮转文件）。日志记录飞书 CLI 读取耗时、QQ 文本/图片操作耗时、重试次数、来源和错误类别，不记录消息正文、图片内容或凭证。网页启动的后台进程也会写入该文件，不依赖终端输出。

转发进程使用 `.qq-forwarder.lock` 做独占锁，避免多个独立会话同时读取和写入游标。飞书消息读取优先使用增量分页：倒序读取 page token，命中本地消息高水位后停止，避免每次无条件拉取完整历史窗口。

运行时文件统一由环境变量 `LARK_QQ_STORAGE_DIR` 控制，包括绑定状态、频道/监听人游标、通知文件、指标和日志。未设置时，`start.command` 和直接运行 Python 命令都会使用用户级目录 `~/Library/Application Support/lark-qq-forwarder`。切换代码工作树时只需保持该环境变量不变，即可继续使用同一份运行时数据。

页面支持为每个 QQ 群绑定维护可读备注（例如“主群”“测试群”）。备注只用于展示和管理，实际投递仍使用内部绑定标识；修改备注或删除绑定前需要先停止转发服务。

控制面运行期间会每 0.5 秒检查转发核心脚本；检测到 `qq_bridge.py` 或 `channel_replay.py` 变化时，若转发服务正在运行会自动重启受控子进程，加载最新代码。网页资源刷新后即可生效；控制面自身代码变化仍需要重启控制面。

同一次通知涉及的来源通过最多 4 个 worker 和有界队列调度；来源内消息仍严格按位置顺序处理，避免突发通知导致任务无限堆积。
