# 飞书与 QQ → QQ 群转发器

这是一个只在本机运行的转发工具。飞书通过用户 API 读取配置的单聊和频道，macOS 飞书通知用于即时唤醒，30 秒巡检负责兜底；QQ 来源读取 macOS 通知中的文本。两路独立采集，先持久化入队，再通过同一个 QQ 官方机器人发送出口投递。

飞书支持普通文本、图片和现有富文本中的文本及图片。文本按飞书 `message_id` 转发；图片先以飞书用户身份下载，再上传 QQ 取得 `file_info`，最后以 `RICH_MEDIA` 发送。

## 平台管理 Tab

Web UI 在两个 Tab 外显示总状态、两路状态、队列计数和统一启停按钮，底部为折叠运行详情；「飞书管理 / QQ 管理」保留各自配置。单路启停和图形化队列恢复入口属于下一阶段。
QQ 管理页提供监听源管理、群的发送源管理和主动发消息：

- 监听源支持新增、编辑、启停和删除，按源群名称和可选发送人配置，也可暂不分配目标群。
- 每个目标群可独立勾选 QQ 监听源，清空来源后保留监听源，只取消向该群自动转发。此视图与监听源中的目标选择同步保存。
- 主动发消息可选择一个有效目标群并输入文本，预览确认后发送，页面显示发送结果。正文最多 3000 字节，通过标准输入传给发送进程，不写入进程参数或运行记录。

规则原子保存到运行时数据目录的 `.qq-notification-sources.json`，刷新或重启控制面后保留；目标群绑定共用，QQ 监听规则与飞书配置独立。

**新版服务运行时会采集已启用源群的后续 QQ 通知，并按规则投递。当前代码已通过模拟验收，QQ 群名、发送人及真实通知端到端仍需在指定测试群验收。**
QQ 第一版仅转发系统展示的通知文本，不支持图片与历史补发。静音、专注模式、前台抑制、隐藏预览、折叠或长文截断都可能造成内容缺失；汇总通知不会推测还原成原消息。
实际源群和发送人字段需要通过真实 QQ 通知验证，不能仅凭手填群名保证匹配。

管理页、两路采集和统一发送已实现；真实联调和后续单路生命周期 UI 的阶段边界见 [统一转发计划](docs/unified-delivery-plan.md)。

## 工作方式

统一服务与并发投递的实现、测试和后续验收见 [统一转发实施计划](docs/unified-delivery-plan.md)。

1. Swift 订阅通知中心 AX 事件。飞书只写无正文唤醒记录；QQ 仅暂存已启用源群的通知，启动时已有通知作为基线，不补发。
2. 飞书按消息位置顺序读取 API，QQ 按通知暂存顺序匹配群名和发送人；各自先把整条消息的目标快照、负载和采集进度原子写入 SQLite。
3. 调度器按“来源 × 目标群”保序，同群最多一个在途请求，跨群最多 4 个并发，默认派发间隔 0.1 秒。失败退避释放发送名额；账号级限流统一等待。
4. 图片下载和上传最多 2 个准备任务，独立于发送名额；图文分段逐段记录确认，重试从未确认分段继续。
5. 所有目标成功或明确跳过后才推进旧确认游标。单条消息最多尝试 5 次，仍失败则跳过该目标的剩余内容，清空负载并继续后续消息；已成功分段不重复发送。同一来源的确认写入失败不阻塞其他来源。

飞书通知与真实消息不是一一对应关系，飞书以 API 消息 ID 去重。QQ 没有真实消息 ID，只对同次可见 AX 节点去重；不同节点的同文通知保留，通知中心重建、进程重启或服务端成功而本机未保存回执时仍可能重复，不承诺恰好一次或无遗漏。

## 首次检查与绑定

创建 Python 环境并安装 QQ 官方 SDK：

```bash
python3.12 -m venv .venv
.venv/bin/pip install -r requirements-qq.txt
```

检查飞书用户授权、Perfecto 固定会话、QQ 凭证和网关：

```bash
.venv/bin/python qq_bridge.py check \
  --lark-profile tenant-105183 \
  --lark-contact Perfecto
```

如尚未绑定 QQ 群：

```bash
.venv/bin/python qq_bridge.py bind
```

如需在保留当前群的同时新增一个 QQ 群绑定，先停止转发服务，再执行：

```bash
.venv/bin/python qq_bridge.py bind --add
```

新增绑定完成后，Perfecto 和已配置频道会向所有 `active` 群发送；每个来源和目标群分别记录已投递消息，某个群发送失败不会阻塞其他群，也不会导致成功群在重试时重复发送。

随后在目标群发送 `@qclaw 绑定测试`。群主还需在手机 QQ 的“群设置 → 机器人 → qclaw → 机器人权限设置”中开启“机器人主动在群聊内发言”。

测试 QQ 主动文本消息：

```bash
.venv/bin/python qq_bridge.py test
```

## 启动转发

推荐双击唯一入口 `start.command`，启动网页控制面：

```bash
./start.command              # 启动网页控制面
```

脚本增量构建 Release 版通知监听器并打开控制面。点击页面「启动服务」后检查环境、执行默认 prime，随后启动 Swift 通知监听和 Python 统一转发器；只打开页面不会自动发送。

启动时不会重放通知文件中的历史唤醒记录。Perfecto、监听人员和四个频道都会从各自已确认的消息位置继续；监听人员与频道会在服务启动时统一立即补扫游标之后的积压消息，之后再由通知即时唤醒，并由低频巡检兜底。

按 `Control+C` 停止。脚本会同时结束通知监听器和转发器。

停止服务后，如果明确需要放弃主联系人未处理的历史记录，并将通知字节位置和主联系人消息位置移到末尾，可手动执行：

```bash
.venv/bin/python qq_bridge.py prime \
  --force-end \
  --lark-profile tenant-105183 \
  --lark-contact Perfecto
```

## 本机 Web 控制面

`start.command` 会启动控制面并自动打开 `http://127.0.0.1:8765`。转发、绑定、补发和测试均从网页操作。

页面提供：

- 总状态和 Swift 通知监听、Python 转发任务的子进程状态；
- 启动、停止、重启操作。启动流程复用现有的 `probe`、`prime`、`run` 命令；
- 只读检查入口，检查失败不会发送 QQ 消息；
- 当前控制面会话中的脱敏事件，例如进程生命周期、只读检查和通知唤醒信号。

写操作同时需要本机同源请求和控制面启动时生成的短期令牌。控制面只会停止本次由它自己启动并持有的子进程，不按状态文件中的 PID 猜测或广泛结束进程；手动启动的独立 CLI 会话仍需在原终端停止。页面和 API 默认不展示 QQ 密钥、完整群/会话标识或本地图片路径；“查看待补发”弹窗仅按用户选择展示待处理消息摘要及图片资源键。

控制面采用独立的 Python 标准库进程管理层，调用统一运行时 CLI；前端采用无构建依赖的静态 HTML、CSS 和 JavaScript，并通过短轮询读取结构化状态。Web UI 不解析终端输出。

## 绑定、测试与初始化

页面提供 CLI 的绑定、主动测试和 prime 操作，不使用外部资源，也不展示 QQ 密钥、完整群标识、会话标识或原始游标。

- 绑定会异步运行现有 `qq_bridge.py bind`。页面会显示未绑定、绑定中和已绑定；绑定中请在目标 QQ 群发送 `@qclaw 绑定测试`，可以取消当前绑定等待。重新绑定会调用现有 `bind --rebind`，页面确认和控制面 API 都要求二次确认。
- 页面提供“监听人员管理”，默认包含 Perfecto；新增人员会保存到本机 `.lark-listeners.json`，页面随后自动重启转发任务完成热更新，无需手动执行命令或重新打开页面。
- 主动消息测试调用现有 `qq_bridge.py test`，页面会明确提示它向真实 QQ 群发送测试消息，并展示进行中、成功或失败。失败时可按引导检查群主动发言权限后重试。
- 游标操作调用现有 `qq_bridge.py prime`。默认 prime 沿用原有语义：首次初始化从最新位置开始，已有游标继续使用，不补发历史消息。`从最新位置开始` 是明确的 `--force-end` 操作，会在二次确认后放弃当前未处理消息并从最新位置开始。
- 启动失败、辅助功能权限失败和子进程退出会给出检查、重试或重启引导。消息仍在重试时不推进确认游标；重试耗尽后按跳过处理。页面不提供已跳过消息的单条重发。

控制面只通过本次会话持有的本地子进程和状态文件判断操作结果，不解析终端输出。绑定、测试和 prime 的状态与事件均由 `/api/status` 以结构化 JSON 返回；所有写请求继续要求 `127.0.0.1` 同源和短期控制令牌。

## 隐私与限制

- 飞书通知 JSONL 只保存唤醒所需的应用名、标题和时间，不保存消息正文或正文派生值。
- 飞书 API 返回的文本只在内存中处理；图片只存在于系统临时目录，发送结束后自动删除。
- `.qq-forwarder-state.json` 保存 QQ 群绑定列表（schema v3）、通知字节位置、飞书会话标识、消息位置和按群投递记录，不保存飞书正文或图片。
- 静音、关闭飞书通知、专注模式、飞书前台抑制通知或辅助功能权限失效时，macOS 可能不产生唤醒事件；飞书仍有 30 秒 API 巡检；QQ 无法从 API 补取缺失通知。
- 当前自动转发 Perfecto 单聊和四个已配置群聊中的普通文本和图片；Perfecto 只转发目标联系人发送的消息，群聊按频道转发可读取到的文本和图片。其他消息类型会记录类型并推进对应游标，不会误当文本发送。

## 转发效率基准与运行时指标

基准运行器位于 `benchmarks/benchmark_forwarder.py`，使用固定消息夹具和假的 QQ 发送端，不会连接真实账号。可分别运行 `--mode legacy` 与 `--mode optimized`，比较批量处理 p50/p95、吞吐、发送数和图片下载次数；具体用法见 `benchmarks/README.md`。

新版运行状态保存在 `.delivery-queue.sqlite3`，`/api/status` 的 `unified` 返回两路状态、心跳和待投递/在途/受阻计数，不返回正文。旧 `.qq-forwarder-metrics.json` 属于旧转发实现，新版控制面不把它作为当前指标。

转发进程同时将排查日志写入 `.qq-forwarder.log`（超过 5 MB 自动保留最近 3 个轮转文件）。日志记录飞书 CLI 读取耗时、QQ 文本/图片操作耗时、重试次数、来源和错误类别，不记录消息正文、图片内容或凭证。网页启动的后台进程也会写入该文件，不依赖终端输出。

转发进程使用 `.qq-forwarder.lock` 做独占锁，避免多个独立会话同时读取和写入游标。飞书消息读取优先使用增量分页：倒序读取 page token，命中本地消息高水位后停止，避免每次无条件拉取完整历史窗口。

运行时文件统一由环境变量 `LARK_QQ_STORAGE_DIR` 控制，包括绑定状态、频道/监听人游标、通知文件、指标和日志。未设置时，`start.command` 和直接运行 Python 命令都会使用用户级目录 `~/Library/Application Support/lark-qq-forwarder`。切换代码工作树时只需保持该环境变量不变，即可继续使用同一份运行时数据。

页面支持为每个 QQ 群绑定维护可读备注（例如“主群”“测试群”）。备注只用于展示和管理，实际投递仍使用内部绑定标识；修改备注或删除绑定前需要先停止转发服务。

控制面运行期间会每 0.5 秒检查转发核心脚本；检测到 `qq_bridge.py` 或 `channel_replay.py` 变化时，若转发服务正在运行会自动重启受控子进程，加载最新代码。网页资源刷新后即可生效；控制面自身代码变化仍需要重启控制面。

飞书来源独立同步，最多 4 个并发读取；QQ 在独立采集任务中处理。持久化队列达到容量时保留进度并背压，不删除未发任务。


## 统一队列、恢复与切换

`run`、`send`、`test` 和频道补发共用队列与单次 SDK 发送适配器。运行时的手动消息由现有服务投递；服务停止时只发送本次请求，使用相同进程锁，不能与旧版本转发器并行抢发。补发仍要求先停止服务，且仅调度勾选消息和目标；存在未选中的更早待发任务时拒绝操作，不入队。选择靠后的历史消息仍沿用原有补发语义：全部目标确认后游标推进到该消息，之前未选中的历史消息不再自动补发。

入队时固定目标快照：后续改路由只影响新采集消息，不能给同一已入队事件追加目标；发送前会检查绑定仍有效，失效目标暂停并保留积压。`prime --force-end` 只放弃主监听联系人的进度及截至最新位置的队列，不影响其他飞书频道或 QQ 来源；默认 prime 保留积压。两种 prime 均要求服务停止。

队列默认最多 10,000 个未完成投递、100,000 个投递记录及 100,000 个采集事件，单条事件负载和元数据合计最多 64 KiB。待投递达到 80% 时总状态提示积压；满容量时保留飞书采集位置和 QQ 暂存文件。已确认且已同步旧游标的记录保留至少 24 小时后分批回收；仍有对应通知文件时保留去重凭据。QQ 暂存目录达到 10,000 项会停止通知进程并提示失败，停止期间的新通知可能无法恢复。

查看至多 1,000 条未完成任务（只显示编号、目标备注和状态，不含正文）：

```bash
.venv/bin/python qq_bridge.py queue-status
```

新版会自动跳过旧队列中已达到 5 次上限的受阻任务，并在页面显示近期回执中的“重试耗尽已跳过”数量；日志记录任务编号和重试上限。账号级退避仍然有效，目标失效仍暂停该群，避免将账号或目标问题当作成功发送。修复原因后，可恢复尚未耗尽的旧受阻任务，或恢复明确暂停的有效目标：

```bash
.venv/bin/python qq_bridge.py queue-retry --delivery-id 123 --delivery-id 124
.venv/bin/python qq_bridge.py queue-retry --binding-id <清单中的绑定编号>
```

恢复命令本身不建立发送连接；服务运行时会接续投递，停止时留待下次启动。消息重试不会解除账号级退避，已取消或已完成任务不能通过恢复命令重发。

新版需要短期保存待发正文：SQLite 权限 `0600`，已完成负载清空并启用 `secure_delete`；QQ 的 `qq-notifications/` 目录权限 `0700`、通知文件 `0600`，成功入队后删除原文件，格式错误保留为 `.invalid` 并提示异常。图片使用临时目录并在正常退出时清理；异常终止可能遗留临时文件。系统备份、快照和磁盘层副本不在清理保证范围内。

从旧版切换时，先停止旧转发服务，再关闭旧控制面并启动新版 `start.command`；保持 `LARK_QQ_STORAGE_DIR` 不变，不要同时启动两个版本。本次开发未执行真实服务切换。新版启动后会继续已有待发积压，正式切换前应核对目标和规则。QQ 真实验收需指定源群、接收测试群及测试消息，再验证文本、同文连续通知、折叠和发送人匹配；模拟测试不能代替该验收。
